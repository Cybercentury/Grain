# Grain — Project Info

> Главный внутренний документ проекта. Используется как техническая память Grain CRM: текущее состояние, бизнес-логика, дизайн-система, ограничения, принятые решения и подробный журнал версий. Перед продолжением разработки сначала сверяться с этим файлом, затем с актуальным `index.html`.

## 1. Паспорт проекта

- **Проект:** Grain
- **Назначение:** B2B CRM для торговли зерном и удобрениями на внутреннем рынке Молдовы.
- **Основной сценарий:** от первого запроса клиента и переговоров до договора, финансового допуска и фактической отгрузки партии.
- **Основной пользователь прототипа:** менеджер продаж.
- **Дополнительные роли в бизнес-процессе:** юрист, коммерческий директор, бухгалтерия.
- **Текущая внутренняя версия / спецификация:** **v0.11.1**
- **Текущая функциональная версия интерфейса:** **v0.11.1**
- **Статус:** статичный интерактивный прототип.
- **Основная ветка:** `main`.
- **Публикация:** GitHub Pages из корня ветки `main`.
- **Рабочий адрес прототипа:** https://cybercentury.github.io/Grain/
- **Дата демонстрационных данных:** 30.09.2026.

Версия **v0.11.0** реализована как Master Data & Field Ownership поверх существующих CRM / Shipment / Finance / MTM / Integrity модулей. Контрагенты и номенклатура получили единые master ID, legalKey для дедупликации, external mappings на CRM / GrainTrack / 1С и правила владения полями.

## 2. Цель системы

Grain должен стать рабочей CRM для компаний, которые покупают, продают и отгружают зерновые культуры и удобрения. Система должна связывать в одной цепочке:

1. клиента;
2. его текущую и потенциальную потребность;
3. переговоры и коммерческое предложение;
4. прогноз объёма будущих отгрузок;
5. договор и согласование документа;
6. финансовое состояние клиента;
7. разрешение конкретной партии к отгрузке;
8. фактическую отгрузку;
9. дальнейший контакт и повторную продажу.

Главный управленческий смысл проекта — менеджер и руководитель должны видеть не только «сумму сделок», а **реальный прогноз тонн, которые могут быть отгружены**, с пониманием стадии переговоров, договорных препятствий и финансовых ограничений.

## 3. Текущая архитектура прототипа

### 3.1. Файлы

Текущая архитектура должна быть постепенно разделена:

- `index.html` — интерфейс, CSS и прикладная JavaScript-логика;
- `data.json` — единый исходный набор демонстрационных бизнес-данных и связей между сущностями;
- `README.md` — краткое описание запуска и возможностей;
- `PROJECT_INFO.md` — этот документ, подробная техническая память проекта.

До v0.7.0 демонстрационные данные были встроены непосредственно в `index.html`. В рамках v0.7.0 принято решение вынести их в `data.json`, чтобы бизнес-данные можно было изменять независимо от HTML и чтобы все разделы CRM использовали единый источник истины.

### 3.2. Технологическая модель

Начиная с v0.7.0, интерфейс должен загружать исходные демонстрационные данные из локального `data.json` через HTTP(S).

Следствие: после перехода на JSON основной поддерживаемый способ запуска — GitHub Pages или простой локальный HTTP-сервер. Открытие `index.html` двойным щелчком через `file://` больше не считается гарантированно поддерживаемым, поскольку браузеры могут блокировать `fetch()` локального JSON.

Текущий прототип:

- не требует сборки;
- не использует внешние JavaScript/CSS-фреймворки;
- не использует внешние шрифты и библиотеки иконок;
- работает прямо из `index.html`;
- публикуется через GitHub Pages;
- хранит все изменения только в памяти открытой страницы;
- после перезагрузки возвращается к исходным демонстрационным данным.

### 3.3. Что пока отсутствует

В прототипе нет:

- серверной базы данных;
- постоянного хранения;
- реальной авторизации;
- разграничения прав на сервере;
- API;
- реальной интеграции с 1С;
- фонового планировщика;
- фактической отправки Email/SMS/Telegram/WhatsApp;
- телефонии;
- загрузки и хранения файлов договоров;
- электронной подписи;
- полноценного журнала фактических складских отгрузок;
- реальных юридически значимых документов.

Все текущие компании, сделки, платежи, решения и уведомления — демонстрационные.

### 3.4. `data.json` как мини-база данных

Начиная с v0.7.0, `data.json` является **единственным каноническим источником демонстрационных бизнес-данных Grain**.

Правила:

- `index.html` загружает данные напрямую из `data.json`;
- бизнес-данные не дублируются в JavaScript-массивах внутри HTML;
- изменение демо-клиентов, сделок, партий, документов или финансовых исходных значений выполняется в первую очередь в `data.json`;
- `PROJECT_INFO.md` хранит **описание схемы и бизнес-правил**, но не копию самих записей;
- XML в проекте не используется и не является частью архитектуры;
- будущий backend должен по возможности сохранить те же идентификаторы и смысловые связи, чтобы переход от JSON-прототипа к API не ломал модель.

#### Каноническая верхнеуровневая структура

```text
data.json
├─ meta
├─ masterData
│  ├─ parties
│  ├─ partyMappings
│  ├─ products
│  ├─ productMappings
│  ├─ fieldOwnership
│  └─ reconciliationRules
├─ clients
├─ deals
├─ shipments
├─ documents
├─ finance
│  ├─ accounts
│  ├─ shipmentFinancials
│  ├─ clearanceRequests
│  └─ cashMovements
├─ market
│  └─ marks
├─ integrity
│  ├─ ruleSettings
│  ├─ weightRecords
│  ├─ invoiceRecords
│  └─ fertilizerQuality
└─ auditSeed
```

#### `meta`

Содержит технические данные набора:

- версия схемы;
- дата демонстрационных данных;
- валюта по умолчанию;
- язык интерфейса;
- список business line;
- при необходимости справочники для демо.

#### `masterData`

Канонический слой общих справочников между CRM, GrainTrack и финансовым учётом.

Содержит:

- `parties` — юридические сущности с immutable `partyId` и `legalKey`;
- `partyMappings` — локальные ID CRM / GrainTrack / 1С;
- `products` — master-номенклатуру с `productId`;
- `productMappings` — локальные product ID разных систем;
- `fieldOwnership` — правила authoritative owner по группам полей;
- `reconciliationRules` — правила duplicate prevention и обязательных mappings.

Для Молдовы demo `legalKey` имеет форму `MD:<13-digit fiscal code>`.

#### `clients`

CRM-представление контрагента для работы менеджера.

Обязательные ключи:

- `id` — локальный CRM ID вида `CL-001`;
- `partyId` — ссылка на `masterData.parties`;
- `name`;
- `type`;
- `region`;
- `manager`;
- `relationshipStatus`;
- настройки контактов и повторной работы.

`clients` больше не считается самостоятельным master-справочником юридических лиц.

Товар не используется как идентификатор клиента. Один клиент может иметь несколько сделок по разным товарам.

#### `deals`

Одна запись на коммерческую возможность.

Обязательные ключи:

- `id` — стабильный ID вида `GR-001`;
- `clientId`;
- `product`;
- `businessLine` — `Grain` или `Fertilizers`;
- `stage`;
- ориентировочный/согласованный объём;
- цена и статус цены;
- переговорные поля;
- следующий шаг;
- ориентировочный период потребности.

**Сделка не хранит массив реальных партий внутри себя.**

Ранние этапы могут иметь `expectedVolume` и `desiredPeriod`, но это не означает, что создана реальная партия.

#### `shipments`

Отдельная сущность реальной плановой партии.

Обязательные ключи:

- `id` — стабильный ID вида `SH-001`;
- `dealId`;
- `clientId`;
- `plannedDate`;
- `plannedQty`;
- `shippedQty`;
- `status`.

Правило появления в плане отгрузок:

- **«Новый запрос»** — Shipment не создаётся;
- **«Потребность уточнена»** — по умолчанию Shipment не создаётся; хранится ожидаемый объём/период в Deal;
- **«Предложение отправлено»** и далее — Shipment может быть создан, если согласован хотя бы ориентировочный график партии;
- в разделе «План отгрузок» отображаются только записи `shipments`, а не любой объём сделки.

Это правило специально устраняет ситуацию, когда `Nord Fertil Demo` на этапе «Новый запрос» уже выглядит как реальная декабрьская отгрузка.

#### `documents`

Документ хранит:

- `id` вида `DOC-001`;
- `clientId`;
- `dealId` или `null`, если документ пока относится только к клиенту;
- тип;
- этап;
- версия;
- текст;
- история согласований.

Если документ относится к конкретной продаже, `dealId` обязателен.

#### `finance.accounts`

Финансовый снимок клиента:

- `clientId`;
- долг;
- просрочка;
- лимит;
- предоплата;
- дата синхронизации;
- статус источника.

Связь выполняется только через `clientId`.

#### `finance.shipmentFinancials`

Первичные управленческие финансовые значения хранятся на уровне партии:

- `shipmentId`;
- финальная цена;
- себестоимость;
- логистика;
- прямые расходы;
- статус значения: План / Подтверждено / Факт;
- срок оплаты;
- статус Financial Lock;
- признак и комментарий незакрытых обязательств.

`businessLine` **не дублируется** в финансовой записи: канонический источник — связанный `Deal.businessLine`.

Cash-in / cash-out также не хранятся как два накопительных поля внутри shipmentFinancials.

#### `finance.cashMovements`

Cash Flow хранится как отдельные датированные движения:

- `id`;
- `shipmentId`;
- `date`;
- `direction`: `in` / `out`;
- `category`;
- `amount`;
- `status`: `planned` / `actual`;
- `source`.

Фильтр периода Cash Flow применяется по `cashMovements.date`, а не по дате Shipment.

Базовые плановые движения коммерческих условий и финансового плана синхронизируются с изменением цены, себестоимости и прямых расходов партии.

#### `market.marks`

Рыночные котировки для MTM:

- `id`;
- `shipmentId`;
- `product`;
- `region`;
- `basis`;
- `deliveryPeriod`;
- `price`;
- `currency`;
- `unit`;
- `source`;
- `observedAt`;
- `status`.

Market mark относится к конкретной Shipment и не является полем сделки. В текущем демо используется один актуальный mark на Shipment; история изменений сохраняется в runtime Audit Trail.

#### `finance.clearanceRequests`

Запрос финансового исключения всегда ссылается на `shipmentId`.

Индекс элемента в массиве, название клиента или строка вида `dealId:index` не считаются постоянным идентификатором.

#### `auditSeed`

Начальные демонстрационные события системного журнала. В рабочем интерфейсе новые записи добавляются в runtime-журнал и должны сохранять ссылку на конкретную сущность по ID.

## 4. Основная бизнес-логика

### 4.1. Воронка продаж

Текущая воронка состоит из шести активных этапов:

| № | Этап | Внутренняя вероятность для прогноза |
|---|---|---:|
| 0 | Новый запрос | 0% |
| 1 | Потребность уточнена | 20% |
| 2 | Предложение отправлено | 40% |
| 3 | Согласование условий | 70% |
| 4 | Контракт подписан | 100% |
| 5 | Исполнение | 100% |

Это **статусы переговоров и исполнения**, а не просто визуальные колонки.

Завершённые, отменённые, проигранные и отложенные сделки пока не вынесены в отдельные конечные статусы и остаются за пределами текущего демо.

### 4.2. Формула прогноза отгрузок

Для выбранного периода система разделяет объём на три части:

- **Факт** — уже отгруженный объём;
- **Контрактный остаток** — неотгруженные тонны сделок на этапах «Контракт подписан» и «Исполнение»;
- **Прогноз переговоров** — неотгруженные тонны более ранних сделок × вероятность этапа.

Упрощённо:

**Ожидаемые отгрузки = контрактный остаток + взвешенный прогноз переговоров.**

Подписанная сделка не должна повторно учитываться как вероятностный прогноз.

### 4.3. Важное правило фильтра периода

Фильтр месяца применяется к расчёту партий и показателей отгрузки.

**Сама воронка не должна скрывать ранние сделки только потому, что их партия находится в другом месяце.** Иначе пропадают «Новый запрос» и «Потребность уточнена», что искажает работу менеджера.

Для воронки сохраняются фильтры по товару и району, но она должна показывать активные сделки всех периодов.

### 4.4. Цена

Есть два принципиально разных состояния цены:

- предварительная;
- фиксированная.

Изменение цены само по себе **не меняет объём в тоннах**.

Истёкший срок предварительной цены создаёт предупреждение, но автоматически не удаляет сделку из прогноза.

### 4.5. Результат переговоров

В сделке хранятся:

- согласованные условия;
- открытые вопросы;
- следующий шаг;
- дата следующего контакта;
- препятствия/блокеры.

Текстовые заметки не должны автоматически менять вероятность этапа. Этап меняется отдельным управленческим действием.

## 5. Основные модули интерфейса

### 5.1. Обзор руководителя

Назначение:

- показать прогноз отгрузок;
- показать факт;
- показать контрактный остаток;
- показать взвешенные переговоры;
- показать риски;
- дать быстрый доступ к проблемным сделкам и следующим действиям.

Главный показатель называется **«Прогноз отгрузок по Молдове»**. При выборе района подпись должна отражать выбранную территорию.

### 5.2. Воронка

Шесть колонок соответствуют текущим активным этапам.

Карточка сделки должна показывать минимум:

- клиента;
- товар;
- район;
- менеджера;
- объём;
- текущий статус;
- открытый вопрос/препятствие;
- следующий шаг.

### 5.3. План партий / отгрузок

Каждая сделка может иметь несколько партий.

Для партии важны:

- дата;
- плановый объём;
- фактически отгруженный объём;
- остаток;
- стоимость остатка;
- финансовый допуск.

Финансовый допуск рассчитывается **для каждой партии отдельно**.

### 5.4. База клиентов

Текущий прототип содержит 10 демонстрационных клиентов.

Клиент связан с:

- типом клиента;
- товаром;
- районом;
- менеджером;
- статусом отношений;
- последним контактом;
- последним заказом;
- правилом следующего контакта;
- каналами уведомления;
- активной сделкой;
- договорами;
- финансовым состоянием и партиями.

**Товар и район являются отдельными полями.**

Поиск клиента должен охватывать:

- название;
- тип клиента;
- товар;
- район;
- статус отношений;
- менеджера.

Отдельные фильтры:

- товар;
- район;
- менеджер;
- статус отношений.

## 6. Логика работы с клиентами и повторными контактами

### 6.1. Правила контакта

В текущем прототипе поддерживаются пять базовых правил:

1. **Сезон** — контакт до ожидаемого сезона закупки.
2. **Повторный заказ** — контакт через заданный интервал после прошлого заказа.
3. **Целевая цена** — контакт, когда текущее предложение соответствует ценовому ориентиру клиента и ещё действительно.
4. **Продолжение контракта** — контакт перед последней плановой партией действующего контракта.
5. **Обещанная дата** — контакт в дату, согласованную с клиентом.

Также возможен перенос контакта менеджером.

### 6.2. Защита от дублирования

Если у клиента уже есть активная сделка, обычное правило контакта не должно создавать параллельное дублирующее напоминание. Используется следующий шаг активной сделки.

Исключение: правило продолжения контракта отдельно ориентируется на последнюю ещё не завершённую партию.

### 6.3. Группы задач

Панель менеджера группирует задачи:

- просрочено;
- сегодня;
- завтра;
- следующие 30 дней.

Дата проверки правил может изменяться в демонстрации независимо от фиксированной даты расчёта отгрузок.

### 6.4. Каналы

Поддерживаемые демонстрационные каналы:

- Email;
- SMS;
- Telegram;
- WhatsApp.

Можно выбрать несколько каналов и посмотреть текст уведомления.

Реальная доставка отсутствует. Повторная демонстрационная отправка одного и того же события теми же каналами блокируется.

## 7. Документооборот

### 7.1. Назначение

Документы связываются с клиентами и, когда применимо, со сделкой.

Текущие типы в демо:

- договор поставки;
- агентский договор.

### 7.2. Маршрут

Базовый маршрут:

**Менеджер → Юрист → Коммерческий директор → Подписание → Подписан.**

Во внутренней модели также присутствуют технические состояния:

- подготовка;
- проверка юристом;
- коммерческое согласование;
- доработка;
- готов к подписанию;
- подписан;
- отклонён.

### 7.3. Версии документа

Принятые правила:

- изменение текста создаёт новую версию;
- согласования относятся к конкретной версии;
- старая версия не может быть согласована вместо текущей;
- возврат обязательно содержит причину;
- после доработки новая версия повторно проходит маршрут;
- на этапах согласования и после подписания текст не редактируется напрямую.

### 7.4. SLA

Демонстрационные сроки:

- юрист — **2 часа**;
- коммерческий директор — **4 часа**.

После достижения срока задача становится просроченной.

Через один час после просрочки создаётся однократная демонстрационная эскалация.

### 7.5. Разделение ролей

Основной экран прототипа моделирует работу менеджера.

Действия юриста и коммерческого директора вынесены в отдельный явно обозначенный демонстрационный блок.

Это важно: **менеджер не должен логически «сам себе» согласовывать документ**, даже если статичный прототип технически позволяет моделировать все роли в одном браузере.


### 7.6. Будущие внешние каналы согласования

В текущем статичном прототипе согласования выполняются только внутри Grain.

После появления защищённого backend/API допускается подключение внешних рабочих каналов, прежде всего:

- Telegram Bot;
- WhatsApp Business;
- при необходимости Email с защищённой ссылкой.

Назначение этих каналов — **не переносить CRM в мессенджер**, а дать сотруднику быстрый внешний интерфейс для уже существующей задачи Grain.

Допустимые действия будущей интеграции:

- получить уведомление о назначенном согласовании;
- открыть актуальную версию документа по защищённой ссылке;
- согласовать документ;
- вернуть документ на доработку с обязательной причиной;
- получить уведомление о новой версии;
- согласовать или отклонить иные внутренние approvals, например срочное финансовое исключение.

Архитектурный принцип:

**Grain остаётся единственным источником истины. Telegram / WhatsApp являются только каналами взаимодействия.**

Перед принятием действия из мессенджера backend обязан проверить:

- идентичность пользователя;
- привязку Telegram/WhatsApp account к пользователю Grain;
- роль и право на конкретное действие;
- Document ID;
- актуальную версию документа;
- текущий этап workflow;
- отсутствие более новой версии;
- состояние задачи и срок действия action token.

После успешной проверки действие записывается в Grain и в Audit Trail с указанием канала-источника.

Старая кнопка из сообщения не может согласовать устаревшую версию документа.

Рекомендуемая схема будущей интеграции:

```text
Grain Workflow
    ↓
Notification / Approval Gateway
    ↓
Telegram / WhatsApp
    ↓
Webhook / secure action
    ↓
Grain API
    ↓
RBAC + version check
    ↓
Workflow update + Audit Trail
```

**Не реализуется в текущей v0.8.x**, потому что безопасная схема требует backend, постоянной БД, авторизации, RBAC, защищённых webhook endpoint и серверного Audit Trail.


### 7.7. Ответы на вопросы руководителя

В интерфейсе Grain создаётся отдельный информационный раздел **«Ответы на вопросы руководителя»**.

Назначение раздела:

- сохранять вопросы руководителя, которые влияют на архитектуру Grain;
- рядом хранить короткий практический ответ;
- фиксировать, какое архитектурное решение из этого следует;
- использовать раздел как внутреннюю базу подготовки к обсуждению системы и как объяснение причин принятых решений.

Раздел **не является бизнес-модулем CRM**, не меняет расчёты, сделки, Shipment или финансовые данные.

Первая зафиксированная запись:

**Вопрос:** чем архитектура товарных потоков принципиально отличается от классической воронки продаж?

**Ответ / архитектурный принцип:**

> Я бы не заменял товарный поток классической воронкой. Я бы разделил два слоя. Воронка отвечает за коммерческую возможность и вероятность продажи, а после формирования обязательства товар проходит через отдельную Shipment-centric модель. Сделка может породить несколько партий, каждая партия имеет собственную логистику, вес, качество, финансовый результат, MTM и контроль целостности. CRM должна связывать эти два слоя, но не смешивать их в один статус.

Следствие для Grain:

- Deal остаётся коммерческой сущностью;
- Shipment является центральной сущностью физического исполнения;
- воронка и товарный поток связаны, но имеют независимые состояния;
- физическое исполнение, качество, логистика, финансы, MTM и Integrity не должны сводиться к одному stage сделки.


### Вопрос 2. Master data между CRM, GrainTrack и финансовым учётом

#### Дословный вопрос руководителя

> «Вы проектировали структуры для 5 направлений бизнеса. Как при этом была организована работа с мастер-данными? Если наша региональная торговля (ПМР и Молдова), закупки удобрений и терминалы используют общих контрагентов и номенклатуру, как вы технически исключите дублирование и рассинхронизацию справочников между CRM, Grain Track и финансовым учетом?»

#### Какие проблемы и вопросы следуют из формулировки

1. Как гарантировать, что один реальный контрагент не станет тремя разными записями в CRM, Grain Track и 1С?
2. Как исключить дубли из-за разных написаний одного названия?
3. Как связать разные локальные ID систем с одной юридической сущностью?
4. Как не создавать отдельного контрагента только потому, что он одновременно Buyer / Supplier / Carrier / Terminal?
5. Как решить ту же проблему для номенклатуры?
6. Какая система имеет право изменять конкретное поле и является источником истины?
7. Как распространять изменение authoritative-поля между системами?
8. Как регулярно обнаруживать пропавшие mappings и расхождения?
9. Как безопасно объединять уже существующие дубли без потери истории и ссылок?

#### Как это реализуется в Grain

**1. Единая идентичность контрагента — реализовано.**  
Каждая юридическая сущность получает immutable `Master Party ID` вида `PTY-001`.

**2. Dedup по юридическому ключу — реализовано.**  
Для Молдовы используется `legalKey = MD:<IDNO>`. Exact duplicate по legalKey блокируется архитектурно; название не является primary key.

**3. Разные ID систем — реализовано.**  
`partyMappings` связывает один `PTY-ID` с локальными CRM / GrainTrack / 1С ID.

**4. Buyer / Supplier / Carrier / Terminal — реализовано моделью Party Roles.**  
Это роли одной master-сущности, а не отдельные карточки юридического лица.

**5. Номенклатура — реализовано тем же принципом.**  
Есть `Master Product ID` и `productMappings` на CRM / GrainTrack / 1С. Название товара не используется как ключ интеграции.

**6. Field Ownership — реализовано.**  
`masterData.fieldOwnership` задаёт authoritative system для master identity, CRM relationships, trading execution и finance/accounting полей.

**7. API / Event Synchronization — архитектурно предусмотрено, backend ещё не подключён.**  
В рабочей системе owner-system публикует изменение по `partyId/productId`; остальные системы обновляют свои read-models, не создавая новую сущность.

**8. Reconciliation — реализован прототип контроля mappings.**  
Master Data Engine проверяет duplicate legalKey, duplicate external ID, missing Party mappings и missing Product mappings. В backend это станет регулярной reconciliation-задачей.

**9. Merge существующих дублей — правило зафиксировано, серверная операция ещё не реализована.**  
При merge выбирается canonical `PTY-ID`, external mappings и ссылки Deal/Shipment/Document переносятся на него, старый master record становится alias/redirect и не удаляется физически, чтобы сохранить Audit Trail.

#### Короткий ответ руководителю

Одна реальная компания и один товар должны существовать как одна master-сущность. CRM, Grain Track и 1С могут иметь свои локальные ID, но они маппятся на единый `Master Party ID` / `Master Product ID`. Для Молдовы `MD:<IDNO>` используется для exact duplicate check. Field Ownership определяет источник истины по полям, изменения распространяются через API/events, а reconciliation регулярно выявляет пропавшие mappings и конфликты. Уже созданные дубли не удаляются вручную — они объединяются через canonical master ID с сохранением истории и ссылок.



### 7.8. Формат карточек «Ответы руководителю»

Начиная с v0.11.1 каждая новая карточка в разделе должна иметь одинаковую структуру:

1. **Дословный вопрос руководителя** — без перефразирования, в отдельном визуально выделенном блоке.
2. **Какие проблемы / вопросы из него следуют** — декомпозиция формулировки на конкретные архитектурные риски.
3. **Как это реализуется в Grain** — короткий ответ по каждому риску с обязательным разделением:
   - уже реализовано в прототипе;
   - архитектурно предусмотрено для backend;
   - ещё не реализовано.
4. **Короткий ответ руководителю** — итоговая версия, пригодная для устного ответа.

Карточки не должны создавать впечатление, что будущие API, event synchronization или server-side merge уже работают в текущем статичном прототипе.

## 8. Финансовый допуск к отгрузке

Финансовый допуск — отдельный контроль каждой партии перед отгрузкой.

### 8.1. Что проверяется

Система проверяет:

1. есть ли подписанный контракт;
2. актуальны ли данные расчётов;
3. есть ли просроченная задолженность;
4. выполнена ли требуемая предоплата;
5. не превышен ли кредитный лимит;
6. учтены ли резервы по другим разрешённым партиям;
7. есть ли действующее исключение коммерческого директора.

### 8.2. 1С

Кнопка импорта из 1С сейчас моделирует три результата:

- текущий долг / новый платёж не подтверждён;
- платёж подтверждён;
- сервер недоступен.

Правила:

- импорт заменяет снимок расчётов;
- повторный импорт не должен повторно вычитать один и тот же платёж;
- ошибка обмена не должна автоматически разрешать отгрузку на основании старых данных;
- данные старше 24 демонстрационных часов требуют новой проверки.

### 8.3. Бухгалтерия

«Связаться с бухгалтерией» создаёт внутреннюю демонстрационную задачу.

Это не звонок и не фактическое сообщение.

### 8.4. Срочное исключение коммерческого директора

Менеджер может создать срочный запрос права отгрузки.

Обязательные свойства исключения:

- относится к **одной конкретной партии**;
- относится к текущим неизменным условиям партии;
- ограничено конкретной суммой;
- действует **24 часа** после решения;
- изменение условий партии аннулирует применимость старого разрешения;
- разрешение не погашает долг;
- разрешение не подтверждает факт оплаты;
- разрешение не заменяет отсутствие подписанного договора.

### 8.5. Резервирование

При передаче разрешённой партии в отгрузку сумма резервируется при проверке кредитного лимита.

Перед фактической фиксацией отгрузки допуск проверяется повторно.


### 8.6. Управленческий финансовый контур v0.7.0

Версия v0.7.0 расширяет существующий финансовый допуск вторым независимым слоем — **контролем качества управленческих данных**.

Передача партии в исполнение должна отвечать на два разных вопроса:

1. **Можно ли отгружать клиенту?** — договор, долг, лимит, предоплата, исключение директора.
2. **Достаточно ли чистых финансовых данных для P&L и Cash Flow?** — финальная цена, себестоимость, логистика, прямые расходы, платёжные сроки и аналитика подразделения.

Эти два допуска не смешиваются. Партия может быть кредитно разрешена, но управленчески не готова из-за отсутствующей себестоимости, логистики или иной обязательной аналитики.

### 8.7. Финансовая иерархия подразделений

Для управленческой отчётности вводится обязательная аналитика бизнес-направления.

Базовая структура:

**Company / Moldova → Sales → Business Line**

Внутри продаж выделяются как минимум:

- **Grain** — зерновые / cereals; внутри направления остаются отдельные товары: пшеница, кукуруза и другие культуры;
- **Fertilizers** — удобрения; внутри направления остаются отдельные виды удобрений;
- **Consolidated** — сводный финансовый уровень, объединяющий Grain + Fertilizers и в будущем другие подразделения компании.

Каждая партия обязана иметь связку:

- юридическое лицо / компания;
- подразделение;
- business line;
- товар;
- клиент;
- менеджер;
- контракт;
- сделка;
- партия.

Минимальные управленческие агрегаты:

- **P&L Grain**;
- **P&L Fertilizers**;
- **P&L Sales** = Grain + Fertilizers;
- **Consolidated P&L**;
- аналогичные срезы для Cash Flow.

Отдельный визуальный финансовый dashboard переносится в **v0.8.0**. В v0.7.0 приоритет — корректность, обязательность, блокировки и журналирование исходных данных на уровне партии.

### 8.8. Финансовые поля партии

Партия становится минимальной единицей управленческого P&L и Cash Flow.

#### Коммерческие данные

- плановый объём;
- фактический объём;
- финальная цена реализации;
- валюта;
- НДС / режим цены;
- условия оплаты;
- плановая дата поступления денег;
- фактические поступления.

#### Себестоимость

- закупочная цена / себестоимость товара;
- стоимость товара по партии;
- источник значения;
- статус значения: **план / подтверждено / факт**.

#### Логистика и прямые затраты

Минимально:

- транспорт;
- погрузка;
- разгрузка;
- хранение;
- лаборатория / анализ качества;
- брокерская или агентская комиссия;
- страхование, если применимо;
- прочие прямые расходы.

Набор категорий должен быть расширяемым без изменения ядра расчёта.

### 8.9. P&L партии

Менеджер не вводит прибыль или маржу вручную.

Производные показатели рассчитываются системой из первичных данных:

**Revenue = фактический объём × финальная цена реализации**

**COGS = фактический объём × подтверждённая себестоимость**

**Direct Costs = логистика + погрузка/разгрузка + хранение + лаборатория + комиссии + страхование + прочие прямые расходы**

**Contribution = Revenue − COGS − Direct Costs**

**Margin % = Contribution / Revenue**, если Revenue > 0.

Ручное редактирование Contribution или Margin % запрещено. Исправляются только первичные данные, и каждое исправление обязательно попадает в журнал.

### 8.10. Cash Flow партии

P&L и Cash Flow считаются отдельно.

Cash Flow должен учитывать:

- предоплату клиента;
- последующие поступления клиента;
- плановые даты cash-in;
- фактические даты cash-in;
- оплату поставщику;
- оплату логистики;
- другие прямые cash-out;
- остаток дебиторской задолженности;
- ожидаемый и фактический net cash flow.

Дата экономического результата и дата движения денег не считаются автоматически одной датой.

### 8.11. Обязательность финансовых данных по этапам

Финансовые поля становятся обязательными по мере продвижения сделки.

| Этап | Минимальные финансовые требования |
|---|---|
| Новый запрос | товар, ориентировочный объём, business line |
| Потребность уточнена | объём, ориентировочная цена |
| Предложение отправлено | цена продажи, ориентировочная себестоимость, ориентировочная логистика |
| Согласование условий | полный прогнозный P&L партии |
| Контракт подписан | финальная коммерческая цена, условия и сроки оплаты |
| Передача в отгрузку | подтверждённая себестоимость, логистика и обязательные прямые затраты |
| Факт отгрузки | фактический объём и доступные фактические расходы |
| Финансовое закрытие партии | полный фактический P&L + Cash Flow либо явно зарегистрированные незакрытые обязательства |

Обычный HTML `required` не является достаточным контролем. В рабочей системе эти правила должны валидироваться на backend.

### 8.12. Financial Lock

После финансового закрытия партии исходные финансовые поля блокируются.

Менеджер после отгрузки/закрытия не может переписывать:

- финальную цену;
- себестоимость;
- логистику;
- прямые расходы;
- фактический объём;
- даты и суммы финансового факта.

Это относится и к другим ролям: обычное редактирование закрытой партии запрещено независимо от должности.

Исправление после закрытия оформляется только через отдельную **корректировку Financial Log**.

Корректировка не уничтожает исходное значение. Она создаёт новую запись с:

- полем;
- исходным значением;
- корректировкой / новым значением;
- причиной;
- автором;
- ролью;
- временем;
- основанием;
- при наличии — ссылкой на документ/платёж/импорт.

### 8.13. Financial Log и системный Audit Trail

**Логирование является ядром Grain CRM.**

Система должна вести неизменяемую историю действий на всех уровнях, а не только историю финансовых полей.

Журнал обязан фиксировать события от:

- менеджера;
- юриста;
- коммерческого директора;
- бухгалтерии;
- администратора;
- импортов;
- экспортов, если они когда-либо будут разрешены отдельным правом;
- интеграции 1С;
- фоновых процессов;
- самой системы.

Минимальная структура записи Audit Log:

- timestamp;
- user / system actor;
- роль;
- тип действия;
- сущность;
- id сущности;
- поле / набор полей;
- **старое значение**;
- **новое значение**;
- источник изменения;
- причина / комментарий, если требуется;
- версия объекта;
- correlation / operation id для пакетных операций.

Нельзя «перезаписывать историю» так, чтобы старое состояние исчезало.

Для финансовых сущностей после Financial Lock любые изменения проходят только через Financial Log / корректировки.

Импорт также считается изменением: система должна хранить, что именно импортировано, откуда, какие поля были изменены, что было до импорта и что стало после него.

Если в будущем появится экспорт данных, сам факт экспорта также должен логироваться: кто, когда, какой набор данных и по какому праву выгрузил.

### 8.14. Статусы качества финансовых данных

Для финансовой партии вводятся состояния:

- **Черновик**;
- **Расчёт неполный**;
- **Расчёт готов**;
- **Подтверждён**;
- **Закрыт / Financial Lock**.

Дополнительно каждое ключевое значение может иметь признак:

- **План**;
- **Подтверждено**;
- **Факт**.

Система не должна молча смешивать плановые и фактические значения в одном итоговом P&L.

## 8.15. Финансовый интерфейс и dashboard v0.8.0

v0.8.0 завершает финансовый контур, специфицированный в v0.7.0, и делает его доступным непосредственно в интерфейсе Grain.

### 8.15.1. Интерфейс финансов партии

Для каждой реальной сущности Shipment должен быть доступен финансовый блок на русском языке.

Минимально отображаются и редактируются до Financial Lock:

- business line: Grain / Fertilizers;
- статус значения: План / Подтверждено / Факт;

- себестоимость на единицу;
- транспорт;
- погрузка / разгрузка;
- хранение;
- лаборатория;
- комиссия;

- фактический cash-out.

### 8.15.2. Автоматический P&L партии

Для расчёта используется плановый объём до появления факта и фактический объём после отгрузки.

Расчётные показатели:

- Revenue;
- COGS;
- Direct Costs;
- Contribution;
- Margin %.

В интерфейсе пользовательские названия должны быть русскими:

- Выручка;

Показываются отдельно:

- фактический cash-in;
- фактический cash-out;
- ожидаемый остаток к получению;
- фактический net cash flow.

P&L и Cash Flow визуально и логически разделяются.

### 8.15.4. Financial Gate

У каждой реальной партии два независимых допуска:

1. **Кредитный допуск** — существующий контроль договора, долга, лимита, предоплаты и исключения директора.
2. **Управленческий финансовый допуск** — контроль полноты финансовых данных для корректного P&L / Cash Flow.

Financial Gate должен выдавать:

- Готово;
- Неполные данные;
- Закрыто;
- список конкретных отсутствующих или некорректных полей.

Financial Gate не должен разрешать финансовое закрытие, если обязательные первичные данные отсутствуют.

### 8.15.5. Financial Lock

Пользователь может финансово закрыть партию только при готовом Financial Gate.

После закрытия:

- первичные финансовые поля становятся read-only;
- прямое изменение данных запрещено;
- сохраняется момент закрытия и actor;
- дальнейшие изменения возможны только через Financial Log.

В статичном прототипе actor моделируется текущей ролью/пользователем интерфейса.

### 8.15.6. Financial Log

После Financial Lock корректировка оформляется отдельной операцией.

Обязательные данные:

- Shipment ID;
- поле;
- старое значение;
- новое значение;
- причина;
- actor;
- роль;
- timestamp;
- источник: пользователь / система / импорт.

Корректировка обновляет актуальное значение для расчётов, но старая запись остаётся в журнале.

### 8.15.7. Общий Audit Trail

### 8.15.8. Финансовый dashboard

## 8.16. v0.8.1 — Financial Integrity Patch

v0.8.1 не добавляет новый бизнес-модуль. Это patch, который делает финансовую логику v0.8 внутренне непротиворечивой перед будущим MTM.

### 8.16.1. Разделение P&L по состоянию данных

Dashboard обязан отдельно показывать:

- **Forecast P&L** — финансовые записи со статусом `План`;
- **Confirmed P&L** — статус `Подтверждено`;
- **Actual P&L** — статус `Факт`.

Система не должна суммировать эти уровни в одну «фактическую выручку».

### 8.16.2. Частичная отгрузка

Для Shipment с частичной отгрузкой одновременно считаются:

- Actual P&L — только по `shippedQty`;
- Open / Forecast P&L — по `plannedQty - shippedQty`;
- Total exposure — по всему плановому объёму.

Открытый остаток не должен исчезать из финансовой картины после первого факта отгрузки.

### 8.16.3. Cash Flow как поток движений

Cash Flow переводится на отдельные датированные движения:

```text
cashMovements[]
- id
- shipmentId
- date
- direction: in | out
- category
- amount
- status: planned | actual
- source
```

Период Cash Flow определяется датой движения денег, а не датой Shipment.

### 8.16.4. Сквозной Financial Lock

Financial Lock защищает не только финансовую форму, но и все поля Shipment, которые влияют на закрытый P&L:

- plannedDate;
- plannedQty;
- shippedQty;
- связанные первичные финансовые поля.

После lock такие изменения запрещены из карточки сделки и других экранов. Корректировка финансовых значений — только через Финансовый журнал. Корректировка факта Shipment в будущем также должна оформляться отдельной контролируемой операцией.

### 8.16.5. Контрактный барьер

Кредитный допуск не может считать договор подписанным только потому, что `deal.stage >= 4`.

Для stage «Контракт подписан» / «Исполнение» требуется связанный документ текущей версии со статусом `signed`.

Если документ отсутствует или ещё на согласовании, кредитный допуск блокируется.

### 8.16.6. Условия финансового закрытия

Financial Lock разрешается только если:

- Financial Gate готов;
- valueStatus = `Факт`;
- Shipment полностью отгружен **или**
- явно зарегистрированы незакрытые обязательства с обязательным комментарием.

### 8.16.7. Shipment Audit Trail

Изменения партии логируются по отдельным полям Shipment:

- plannedDate;
- plannedQty;
- shippedQty;
- status.

Журнал не должен ограничиваться одной непрозрачной записью об изменении массива `parts`.

### 8.16.8. Business line

`Deal.businessLine` является каноническим источником business line для финансовой аналитики.

Дублирующее поле businessLine внутри shipmentFinancials не должно использоваться как независимый источник истины.

### 8.16.9. Встроенный словарь терминов

Требование из раздела 12.7 реализуется в интерфейсе v0.8.1.

Единый tooltip-механизм должен поддерживать минимум:

- MTM;
- P&L;
- Cash Flow;
- COGS;
- Contribution;
- Финансовая проверка;
- Финансовая блокировка;
- Финансовый журнал;
- Audit Trail.

## 8.18. v0.9.0 — MTM / Mark-to-Market

MTM — рыночная переоценка открытой товарной позиции. В Grain он не заменяет P&L и Cash Flow, а добавляет отдельный слой текущей рыночной стоимости открытого объёма.

### 8.18.1. Базовая единица

MTM рассчитывается на уровне **открытого остатка Shipment**:

```text
openQty = max(plannedQty - shippedQty, 0)
```

Текущий прототип моделирует продажи, поэтому:

```text
MTM = (salePrice - marketPrice) × openQty
```

Если позже появится side = BUY:

```text
BUY MTM = (marketPrice - purchasePrice) × openQty
```

Полностью исполненная партия имеет openQty = 0 и MTM = 0.

### 8.18.2. Market Mark

Рыночная котировка хранится отдельно от сделки и партии.

Минимальная структура:

- `id`;
- `shipmentId`;
- `product`;
- `region` / basis;
- `deliveryPeriod`;
- `price`;
- `currency`;
- `unit`;
- `source`;
- `observedAt`;
- `status`: current / stale.

Для текущего демо один Shipment связан с одним актуальным market mark. В будущем возможна полноценная история котировок.

### 8.18.3. План отгрузок

В «Плане отгрузок» добавляются:

- открытый остаток;
- цена сделки;
- рыночная цена;
- MTM партии;
- актуальность котировки.

Это основной оперативный экран рыночного риска.

### 8.18.4. Карточка сделки

Deal показывает:

- общий открытый объём;
- общий MTM;
- таблицу Shipment с market price и MTM;
- источник и timestamp котировки.

MTM сделки = сумма MTM открытых Shipment этой сделки.

Ранняя потребность без Shipment не получает официальный MTM.

### 8.18.5. Финансы

Dashboard получает отдельные показатели:

- Open Exposure, т;
- Unrealized MTM;
- Actual P&L;
- Total Economic P&L = Actual P&L + Unrealized MTM.

Forecast / Confirmed P&L остаются отдельными сценарными показателями и не подменяют Actual P&L.

Агрегация: Grain / Fertilizers / Sales / Consolidated.

### 8.18.6. Audit Trail

Изменение market mark логируется с:

- old price;
- new price;
- source;
- observedAt;
- actor / system actor;
- market mark ID;
- связанным Shipment;
- причиной при ручном изменении.

### 8.18.7. Терминология

MTM добавляется в единый словарь интерфейса:

**MTM (Mark-to-Market) — рыночная переоценка открытой позиции. Показывает нереализованную прибыль или убыток относительно текущей сопоставимой рыночной цены.**

## 8.19. v0.10.0 — Integrity & Risk Control

v0.10.0 добавляет контроль целостности товарного потока поверх существующей цепочки:

```text
Deal → Contract → Shipment → Logistics / Weight → Quality / DV → Invoice / Finance → Cash Flow → MTM
```

Главный принцип: **ошибка в одном блоке должна быть обнаружена до того, как она незаметно повлияет на физическое исполнение или финансовый результат.**

### 8.19.1. Integrity Gate

Для каждой реальной Shipment рассчитывается отдельный статус:

- **Готово** — критических расхождений нет;
- **Предупреждение** — есть некритическое отклонение / устаревшие данные;
- **Критично** — обнаружено расхождение, которое может привести к финансовой потере или неверному физическому исполнению.

Integrity Gate не заменяет:

- кредитный / shipment clearance;
- Financial Gate;
- MTM.

Это отдельный контроль целостности.

### 8.19.2. Источники проверки

В v0.10.0 в `data.json` добавляется отдельный раздел `integrity`:

```text
integrity
├─ weightRecords
├─ invoiceRecords
├─ fertilizerQuality
└─ ruleSettings
```

#### weightRecords

Минимальные поля:

- `id`;
- `shipmentId`;
- `grossKg`;
- `tareKg`;
- `netKg`;
- `observedAt`;
- `source`;
- `status`.

#### invoiceRecords

- `id`;
- `shipmentId`;
- `qty`;
- `unitPrice`;
- `amount`;
- `status`;
- `source`.

#### fertilizerQuality

Для Fertilizers:

- `shipmentId`;
- заявленная / контрактная формула;
- лабораторные показатели;
- tolerance;
- правила стоимостной корректировки по дефициту компонента.

### 8.19.3. Контроль веса

Integrity Engine должен проверять:

1. `netWeight <= plannedQty` с учётом допустимого tolerance;
2. invoice quantity не должна расходиться с подтверждённым net weight сверх tolerance;
3. net weight не должен превышать остаток контракта / Shipment;
4. отрицательные или физически невозможные gross / tare / net запрещены.

Потенциальное денежное воздействие:

```text
weightExposure = abs(weightDifference) × relevantPricePerTon
```

где relevantPricePerTon берётся из связанной финансовой / коммерческой записи.

### 8.19.4. Контроль ДВ минеральных удобрений

Для NPK и других удобрений система не хранит вручную рассчитанный ДВ как независимую истину.

Расчёт:

```text
activeSubstanceTons = shipmentTons × nutrientPercent / 100
```

Integrity Engine сравнивает:

- контрактный %;
- лабораторный %;
- tolerance;
- рассчитанное количество ДВ;
- стоимостное правило корректировки.

При дефиците компонента создаётся Exception с:

- компонентом;
- contract %;
- lab %;
- deficit percentage points;
- deficit active-substance tons;
- оценкой financial exposure.

### 8.19.5. Контроль рыночных данных

Integrity Engine должен создавать предупреждение, если:

- market mark отсутствует;
- market mark помечен stale;
- timestamp котировки старше допустимого окна из ruleSettings.

Это не меняет MTM автоматически, а указывает, что MTM основан на потенциально ненадёжной котировке.

### 8.19.6. Exception

Exceptions рассчитываются из исходных данных и не должны вручную дублировать результат проверки.

Минимальная модель runtime Exception:

- `id`;
- `shipmentId`;
- `category`;
- `severity`;
- `title`;
- `details`;
- `difference`;
- `financialImpact`;
- `sourceIds`;
- `blocking`;
- `detectedAt`.

### 8.19.7. Обзор / Dashboard руководителя

На «Обзоре» появляется отдельный блок **«Контроль целостности и рисков»**:

- количество критических Exceptions;
- количество предупреждений;
- сумма потенциального финансового воздействия;
- количество заблокированных / проблемных Shipment;
- список наиболее существенных отклонений, отсортированный по severity и financialImpact.

Руководитель должен видеть не все нормальные операции, а прежде всего Exceptions.

### 8.19.8. План отгрузок

В таблицу Shipment добавляется отдельная колонка **Integrity Gate**.

Примеры:

- `Готово`;
- `Предупреждение · 1`;
- `Критично · 2`.

Нажатие открывает детализацию проверки партии.

### 8.19.9. Стоимостная оценка риска

Ключевой принцип:

**Exception → Financial Impact.**

Система должна по возможности переводить физическое или качественное отклонение в MDL.

Это оценка потенциального воздействия, а не бухгалтерски признанный убыток.

### 8.19.10. Демо-кейсы v0.10.0

Для проверки интерфейса и алгоритма в `data.json` создаются несколько искусственных операций:

1. зерновая Shipment с net weight выше планового объёма;
2. Shipment с invoice quantity, отличающимся от net weight;
3. Fertilizers Shipment с лабораторным N/P₂O₅ ниже контрактного NPK;
4. Shipment с устаревшей market mark.

Все кейсы должны быть явно демонстрационными и должны генерировать Exceptions алгоритмом, а не статичным текстом.

## 8.20. v0.11.0 — Master Data & Field Ownership

v0.11.0 вводит отдельный слой мастер-данных для общих контрагентов и номенклатуры между CRM, GrainTrack и финансовым учётом.

Главный принцип:

**одна реальная юридическая сущность = один Master Party, даже если в разных системах у неё разные локальные ID.**

### 8.20.1. Master Party ID и Legal Key

Используются два разных идентификатора:

- `partyId` — внутренний неизменяемый ID вида `PTY-001`;
- `legalKey` — юридический уникальный ключ для дедупликации, например `MD:1000000000001`.

`partyId` используется во внутренних связях Grain.

`legalKey` строится как:

```text
<jurisdiction>:<fiscal / registration code>
```

Для Молдовы в демо:

```text
MD:<IDNO>
```

Причина разделения: fiscal / registration code является естественным бизнес-ключом для сверки, но архитектура не должна привязывать все внутренние связи к изменяемому внешнему реквизиту.

### 8.20.2. External ID Mapping

Одна Party может иметь разные ID в системах:

```text
PTY-001
├─ CRM: CL-001
├─ GrainTrack: GT-PTY-001
└─ 1C: 1C-PTY-001
```

Интеграции не должны искать контрагента по названию.

Все обмены выполняются через `partyId` / `legalKey` и таблицу mappings.

### 8.20.3. Roles вместо отдельных справочников

Party имеет роли:

- Buyer;
- Supplier;
- Carrier;
- Terminal;
- Broker;
- Laboratory;
- Agent;
- Prospect.

Одна Party может иметь несколько ролей одновременно.

«База клиентов» в CRM становится представлением Master Parties с ролями Buyer / Prospect, а не отдельным независимым справочником юридических лиц.

### 8.20.4. Master Products

Та же модель применяется к номенклатуре.

`productId` вида `PRD-001` является каноническим ID продукта.

Примеры:

- PRD-001 — Пшеница;
- PRD-002 — Кукуруза;
- PRD-003 — NPK 10-26-26.

Каждый продукт имеет external mappings для CRM / GrainTrack / 1С.

Название товара не используется как ключ синхронизации.

### 8.20.5. Field Ownership

В `masterData.fieldOwnership` фиксируется владелец каждого класса полей.

Принцип:

- юридические реквизиты и банковские данные — Master / финансовый учёт;
- relationship status, manager, контакты и CRM notes — CRM;
- торговые контракты, Shipment, логистика и MTM — GrainTrack / trading layer;
- бухгалтерские остатки, задолженность и проводки — 1С / finance;
- системные master IDs и mappings — Master Data Engine.

Система, не являющаяся owner поля, не должна молча перезаписывать его как новый источник истины.

### 8.20.6. Duplicate Prevention

Перед созданием новой Party:

1. нормализуется jurisdiction;
2. проверяется fiscal / registration code;
3. строится legalKey;
4. выполняется exact lookup по legalKey;
5. при совпадении создание второй Party блокируется;
6. fuzzy name matching используется только как предупреждение, а не как основание для автоматического merge.

### 8.20.7. Master Data Reconciliation

В CRM должен быть контроль:

- отсутствует mapping в GrainTrack;
- отсутствует mapping в 1С;
- legalKey конфликтует;
- owner field расходится между системами;
- товар не имеет master product mapping.

Такие случаи выводятся как Master Data Exceptions.

### 8.20.8. Текущая миграция прототипа

Для v0.11.0:

- существующие `clients` получают `partyId`;
- текущие названия и CRM-поля продолжают работать;
- создаётся `masterData.parties`;
- создаётся `masterData.partyMappings`;
- создаётся `masterData.products`;
- создаётся `masterData.productMappings`;
- создаётся `masterData.fieldOwnership`;
- существующие Deal получают `productId`;
- UI получает отдельный экран Master Data / mappings и вывод Master Party ID в карточке клиента.

## 9. Основные сущности данных

Начиная с v0.7.0 все демонстрационные сущности должны иметь стабильные ID и связываться по ID, а не по совпадению названий.

Обязательная цепочка:

**Client → Deal → Shipment → Document → Financial entries / Clearance**

Ключевые связи:

- `clientId` — единый идентификатор клиента;
- `dealId` — сделка принадлежит конкретному клиенту;
- `shipmentId` — реальная партия принадлежит конкретной сделке;
- `documentId` — документ связан с клиентом и, когда применимо, со сделкой;
- финансовые записи и допуски ссылаются на `shipmentId`, а не на позицию партии в массиве.

Название клиента, товар или индекс массива не являются ключом связи.

Ранние стадии воронки могут иметь ориентировочный спрос/объём и желаемый период, но это ещё не должно автоматически создавать реальную запись Shipment в плане отгрузок.

При дальнейшем переходе к backend рекомендуется сохранить текущие смысловые сущности, даже если структура полей будет нормализована.

### Client

Клиент/контрагент:

- id;
- название;
- тип;
- товар;
- район;
- ответственный менеджер;
- статус отношений;
- история контактов;
- правило следующего контакта;
- каналы;
- ценовой ориентир;
- сезонность.

### Deal

Активная коммерческая возможность:

- клиент;
- товар;
- район;
- менеджер;
- стадия;
- цена;
- признак фиксации цены;
- срок цены;
- следующий контакт;
- следующий шаг;
- согласованные условия;
- открытые вопросы;
- блокеры;
- партии.

### Shipment / Deal Part

Отдельная партия:

- резерв суммы;

Результат правила контакта или следующего шага активной сделки.

- клиент;

- ответственный;

- версии;
- согласования;
- история;
- срок исполнения;
- причина возврата/отклонения.

Последний снимок расчётов клиента:

- долг;
- просроченный долг;
- лимит;
- предоплата;
- дата синхронизации;
- статус ошибки обмена.

### Clearance Request

Запрос исключения на конкретную партию:

- партия;
- сумма;
- fingerprint условий;
- причина;
- решение;
- комментарий директора;
- срок действия.


### Financial Entry / Financial Log

Запись первичного финансового значения или корректировки:

- исходное значение;
- новое значение / сумма корректировки;
- валюта;

- источник;
- автор / system actor;
- роль;
- timestamp;
- причина;
- версия;
- immutable audit reference.

## 10. Роли и будущая модель доступа

### Менеджер продаж

Должен работать с:

- клиентами;
- сделками;
- переговорами;
- партиями;
- следующими контактами;
- подготовкой документов;
- запросами в бухгалтерию;
- запросами исключения директору.

### Юрист

Должен видеть и обрабатывать только юридически релевантные задачи и документы.

### Коммерческий директор

Должен:

- согласовывать коммерческие условия документов;
- рассматривать срочные исключения на отгрузку;
- видеть эскалации.

### Бухгалтерия

Должна:

- подтверждать/уточнять расчёты;
- работать с задолженностью и оплатой;
- быть источником финансовой информации, потенциально через 1С.

### Важный будущий принцип

В рабочей CRM доступ должен ограничиваться **на сервере**, а не только скрытием кнопок в интерфейсе.

## 11. Конфиденциальность и экспорт

Принятое решение:

- в интерфейсе менеджера нет кнопок CSV-экспорта;
- кнопки сброса демонстрационных данных также удалены;
- весь связанный код экспорта удалён из текущего прототипа.

Причина — клиентская база и коммерческие данные являются конфиденциальными, поэтому нельзя закладывать модель, где любой менеджер в один клик выгружает всю базу.

При этом важно помнить: **отсутствие кнопки экспорта в статичном HTML не является настоящей защитой данных.**

Рабочая версия потребует:

- серверной авторизации;
- RBAC/прав доступа;
- ограничения массовой выгрузки;
- аудита действий;
- серверного контроля API;
- при необходимости отдельных прав на экспорт для руководителей/администраторов.

- при наведении мыши на профессиональный термин появляется компактная подсказка над термином;
- та же подсказка должна быть доступна по keyboard focus;
- определение должно состоять из короткой расшифровки и простого объяснения бизнес-смысла;
- подсказка не должна требовать перехода на отдельную страницу;
- терминология должна объясняться на русском языке;
- техническое английское сокращение можно сохранять, если оно стандартно для отрасли.

Базовый словарь:

- **MTM** — Mark-to-Market / рыночная переоценка открытой позиции;
- **P&L** — Profit & Loss / отчёт о прибылях и убытках;
- **Cash Flow** — движение денежных средств;
- **COGS** — себестоимость реализованного товара;
- **Contribution** — маржинальный доход после себестоимости и прямых расходов;
- **Финансовая проверка** — контроль полноты управленческих данных партии;
- **Финансовая блокировка** — запрет прямого изменения финансового факта после закрытия;
- **Финансовый журнал** — единственный путь корректировки закрытой партии;
- **Журнал аудита / Audit Trail** — история действий, изменений и источников данных.

Система должна быть расширяемой: новые термины добавляются в единый словарь, а не реализуются отдельной логикой tooltip для каждого экрана.

## 13. Ключевые продуктовые инварианты

Следующие правила считаются принятыми и не должны меняться случайно при следующих итерациях:

1. Воронка содержит шесть активных этапов от «Нового запроса» до «Исполнения».
2. Ранние сделки не скрываются фильтром месяца.
3. Месяц относится к партиям и прогнозу отгрузок, а не к существованию сделки.
4. Товар и район — разные поля.
5. Поиск клиентов должен работать по всем основным полям, а не только по названию.
6. CSV/массовый экспорт для обычного менеджера отсутствует.
7. Цена и объём — независимые параметры.
8. Заметки переговоров не меняют вероятность автоматически.
9. Активная сделка не создаёт дублирующий обычный reminder клиента.
10. Согласование договора относится к конкретной версии.
11. Менеджер не должен логически исполнять роль юриста/директора в рабочей архитектуре.
12. Финансовый допуск проверяется на уровне партии.
13. Исключение директора не заменяет подписанный договор.
14. Исключение не погашает задолженность и не подтверждает оплату.
15. Изменение условий партии делает старое исключение неприменимым.
16. Перед фактической отгрузкой допуск проверяется повторно.
17. Все демо-интеграции должны быть явно обозначены как демонстрационные, пока нет реального backend/API.
18. Каждая партия обязана принадлежать бизнес-направлению; минимум Grain или Fertilizers.
19. P&L и Cash Flow строятся из первичных финансовых данных партии, а не из вручную введённой маржи.
20. После Financial Lock первичные финансовые поля не редактируются напрямую.
21. Любая корректировка закрытой партии создаётся только через Financial Log и не уничтожает предыдущие значения.
22. Audit Trail обязателен для действий пользователей, руководителей, бухгалтерии, интеграций, импорта/экспорта и системы.
23. Любое изменение проекта — код, UI, данные, формулы, роли, бизнес-правила, воронка, дизайн или стандартные демо-значения — обязательно документируется в PROJECT_INFO.md в том же изменении/коммите.
24. Изменение проекта без соответствующей записи в PROJECT_INFO.md считается незавершённым и не должно считаться принятой версией.
25. Основной язык проекта на текущем этапе — **русский**: интерфейс, пользовательские статусы, подсказки, предупреждения, ошибки, финансовые названия и проектная документация ведутся на русском языке.
26. Технические идентификаторы кода, имена переменных, сущностей и API могут оставаться на английском для удобства разработки, но не должны без необходимости попадать в пользовательский интерфейс.
27. Демонстрационные бизнес-данные должны храниться в едином `data.json`, а не дублироваться по разделам интерфейса.
28. Все связи между клиентами, сделками, партиями, документами и финансовыми записями строятся по стабильным ID.
29. Название клиента и индекс партии в массиве не используются как постоянные идентификаторы.
30. Ранний запрос или ориентировочная потребность не должны автоматически попадать в реальный план отгрузок как Shipment.
31. `data.json` является единственной мини-базой бизнес-данных текущего прототипа; `index.html` не должен содержать параллельные копии исходных клиентов/сделок/партий.
32. XML не используется в Grain и не входит в текущую архитектуру данных.
33. Профессиональная терминология интерфейса должна иметь встроенные русскоязычные hover/focus-подсказки из единого словаря терминов.
34. Cash Flow фильтруется по дате денежного движения, а не по дате Shipment.
35. Стабильный `shipmentId` сохраняется при любом runtime-редактировании сделки и не пересоздаётся из индекса массива.
36. Для этапов «Контракт подписан» и «Исполнение» финансовый допуск требует реально связанный документ со статусом `signed`, а не только номер стадии Deal.
37. MTM рассчитывается только на открытый остаток Shipment: `max(plannedQty - shippedQty, 0)`.
38. Рыночная котировка MTM обязана иметь источник и timestamp; изменение market mark записывается в Audit Trail с old/new snapshot.
39. Forecast / Confirmed / Actual P&L являются разными состояниями и не должны молча суммироваться в «фактическую выручку».
40. Для частично исполненной партии Actual P&L относится к отгруженному объёму, а открытый остаток продолжает существовать как confirmed/open exposure и участвует в MTM.
41. Integrity Gate является отдельным контролем и не заменяет Financial Gate, shipment clearance или MTM.
42. Exceptions вычисляются из исходных weight / invoice / quality / market данных и не хранятся как вручную подготовленные статусы.
43. Критическое Integrity-отклонение может блокировать shipment clearance и финансовое закрытие партии.
44. Физическое или качественное отклонение по возможности переводится в потенциальное финансовое воздействие в MDL.
45. Потенциальное воздействие Integrity — управленческая оценка риска, а не признанный бухгалтерский убыток.
46. Проверка ДВ использует централизованный расчёт количества действующего вещества из массы Shipment и процента компонента; вручную рассчитанный ДВ не является отдельным источником истины.
47. Руководитель на обзоре должен видеть Exceptions по severity и финансовому воздействию, а не перечень всех нормальных операций.

## v0.9.0 — 2026-10-01 — MTM / рыночная переоценка

**Статус:** реализовано в текущем статичном прототипе.

### Реализовано

MTM отображается в трёх рабочих точках:

1. **План отгрузок**
   - рыночная цена каждой Shipment;
   - MTM партии;
   - открытый остаток;
   - переход в финансовую карточку.

2. **Карточка сделки**
   - общий открытый объём Deal;
   - суммарный MTM Deal;
   - детализация по Shipment;
   - цена сделки / market price / MTM каждой партии.

3. **Финансы**
   - Open Exposure;
   - Forecast P&L;
   - Confirmed P&L;
   - Actual P&L;
   - Unrealized MTM;
   - Total Economic P&L = Actual P&L + Unrealized MTM;
   - агрегаты Grain / Fertilizers / Sales / Consolidated.

### Формула MTM текущего SELL-прототипа

```text
openQty = max(plannedQty - shippedQty, 0)
MTM = (finalSalePrice - marketPrice) × openQty
```

Полностью исполненная партия имеет MTM = 0.

### Market marks

В `data.json` добавлен раздел `market.marks`.

Текущий демо-набор содержит 5 котировок — по одной на каждую реальную Shipment. Все котировки помечены как демонстрационные и содержат:

- Shipment ID;
- товар;
- регион / basis;
- delivery period;
- цену;
- валюту / единицу;
- источник;
- observedAt;
- status.

Ручное изменение существующего market mark требует причины. Audit Trail сохраняет полный old/new snapshot, источник и причину.

### Одновременно завершён v0.8.2 Financial Integrity

#### Финансовая карточка Shipment

У каждой реальной партии доступна финансовая карточка.

До финансового закрытия можно изменять:

- статус значения: План / Подтверждено / Факт;
- финальную цену;
- себестоимость на тонну;
- транспорт;

- фактический cash-out.

Business line берётся из Deal и отдельно в финансовой карточке не редактируется, чтобы не создавать расхождение между торговой и финансовой моделью.

#### Автоматический P&L

Система автоматически рассчитывает:

- Выручку;
- Себестоимость;
- Прямые расходы;
- Маржинальный доход / Contribution;
- Маржу %.

Ручного поля «Маржа» нет.

До появления фактической отгрузки расчёт использует плановый объём Shipment; после появления фактического объёма — фактически отгруженный объём.

#### Cash Flow

Отдельно от P&L рассчитываются и показываются:

- плановый cash-in;
- фактический cash-in;
- фактический cash-out;
- остаток к получению;
- фактический net cash flow.

#### Финансовая проверка

Финансовая проверка считается готовой, если:

- есть финальная цена > 0;
- есть себестоимость > 0;
- логистика содержит корректное значение;
- задана корректная плановая дата cash-in;
- определён допустимый business line;
- финансовые значения больше не находятся только в статусе «План».

Статус «План» специально считается недостаточным для готового управленческого Financial Gate, даже если все числовые поля заполнены.

#### Финансовая блокировка

Для финансового закрытия партии одновременно необходимы:

- готовая финансовая проверка;
- статус значения **«Факт»**.

После закрытия:

- первичные финансовые поля становятся недоступными для прямого редактирования;
- сохраняется событие закрытия;
- дальнейшие изменения выполняются только через Финансовый журнал.

#### Финансовый журнал

Для закрытой партии доступна отдельная форма корректировки.

Обязательны:

- изменяемое поле;
- новое значение;
- причина корректировки.

Система:

- сохраняет старое значение;
- сохраняет новое значение;
- записывает actor и роль;
- записывает timestamp;
- указывает источник «Финансовый журнал»;
- не позволяет корректировкой сделать обязательные финансовые данные некорректными.

#### Audit Trail

В интерфейсе появился видимый журнал аудита текущей сессии.

Он получает события:

- изменения сделки;
- изменения клиента;
- действий документооборота через существующий workflow log;
- действий существующего финансового допуска;
- демонстрационного импорта 1С через финансовый контур;
- изменения финансовых данных Shipment;
- финансового закрытия;
- корректировок Финансового журнала;
- системных seed-событий из `data.json`.

Важно: в v0.8 Audit Trail является **runtime-демонстрацией**. Он не является защищённым неизменяемым серверным аудитом и исчезает после перезагрузки вместе с остальными runtime-изменениями.

P&L и Cash Flow разделены.

Для партии должны учитываться:

- cash-in;
- cash-out;
- предоплата;
- расчёты с поставщиком;
- логистика;
- даты платежей;
- дебиторская задолженность.

### Financial Gate

К существующему кредитному допуску добавляется независимый контроль полноты управленческих данных.

Кредитно разрешённая партия не должна автоматически считаться готовой для финансовой отчётности.

### Financial Lock

После финансового закрытия партии первичные финансовые поля блокируются.

Менеджер и другие обычные роли не могут переписывать закрытый финансовый факт.

### Financial Log

Все корректировки после закрытия выполняются только через отдельную запись Financial Log.

Исходные значения сохраняются.

### Audit Trail как ядро системы

Зафиксировано обязательное логирование всех действий:

- менеджера;
- директора;
- юриста;
- бухгалтерии;
- администратора;
- импорта;
- экспорта;
- 1С;
- системных и фоновых операций.

Каждая запись должна хранить old value → new value, actor, role, timestamp, source и версию объекта.

### Project governance

Зафиксировано обязательное правило:

**любое изменение проекта обязано быть подробно записано в PROJECT_INFO.md в том же рабочем цикле/коммите.**

### Основной язык

Зафиксирован русский как основной язык текущей реализации Grain. Новые пользовательские элементы v0.7.0 — P&L, Cash Flow, Financial Gate, Financial Lock, Financial Log и Audit Trail — должны отображаться на русском языке; английские названия допустимы только как внутренние технические термины/идентификаторы.

### Единый источник бизнес-данных

Принято архитектурное решение вынести демонстрационные данные из `index.html` в отдельный `data.json`.

Цели:

- единый источник истины для всех разделов CRM;
- устранение дублирования;
- стабильные связи через ID;
- возможность менять демонстрационные данные без редактирования HTML;
- подготовка структуры к будущему backend/API.

Отдельно зафиксировано, что «Новый запрос» и другая ранняя потребность могут существовать без реальной партии. В план отгрузок попадают только сущности Shipment, созданные по бизнес-правилам, а не любой ориентировочный объём из сделки.

Особенно это касается:

- финансовой логики;

Изменение без записи в PROJECT_INFO.md считается незавершённым.

## v0.6.0 — 2026-09-30 — Финансовый допуск партий и переработка воронки

**Тип:** крупное функциональное обновление.

### Финансовый допуск

Для каждой партии добавлен статус допуска к отгрузке.

Проверяются:

- подписанный контракт;
- актуальность финансовых данных;
- общий долг;
- просроченный долг;
- предоплата;

Добавлены сценарии:

- долг без нового платежа;
- подтверждённый платёж;
- ошибка сервера.

Повторный импорт заменяет снимок и не должен повторно применять один и тот же платёж.

### Связь с бухгалтерией

Добавлено создание внутренней задачи бухгалтерии для уточнения оплаты.

### Срочный запрос директору

Менеджер может запросить у коммерческого директора исключение на конкретную партию.

Исключение:

- требует обязательного основания;
- относится только к одной партии;
- ограничено суммой;
- действует 24 часа;
- зависит от fingerprint условий партии;
- становится неприменимым после изменения условий;
- не заменяет договор;
- не погашает задолженность.

### Резерв

При передаче партии в отгрузку сумма резервируется для расчёта доступного лимита.

### Защита факта отгрузки

Попытка увеличить фактически отгруженный объём требует действующего допуска.

### Воронка

Воронка окончательно закреплена как шесть этапов:

1. Новый запрос;
2. Потребность уточнена;
3. Предложение отправлено;
4. Согласование условий;
5. Контракт подписан;
6. Исполнение.

Убрана логика, из-за которой ранние стадии могли пропадать из воронки из-за фильтра выбранного месяца.

### Клиенты и документы

- товар и район разделены;
- расширен поиск клиентов;
- добавлены отдельные фильтры;
- расширен поиск и фильтрация документов.

### Конфиденциальность

По отдельному продуктовому решению:

- удалены CSV export;
- удалены кнопки reset;
- удалён соответствующий код.

Причина — интерфейс обычного менеджера не должен провоцировать массовую выгрузку клиентской базы.

### Отраслевые ориентиры

При формировании этапов учитывались идеи GrainTrack For Traders и Barchart: возможность → предложение → подтверждение сделки → контракт → исполнение.

Это использовано как ориентир, а не как утверждение о едином отраслевом стандарте.

### Регрессия

- обработку ошибки сервера;
- бухгалтерские обращения;
- исключения;
- срок исключения;

- все шесть этапов;
